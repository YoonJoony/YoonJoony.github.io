## 2. 추가로 반드시 알아야 할 포인트

여기부터는 항목을 공부하면서 함께 확인해야 할 실수 방지 기준입니다.

### ① `None`, 빈 문자열, 숫자 0을 같은 의미로 처리하지 않기

다음 값들은 조건문에서 모두 거짓으로 평가될 수 있지만, 데이터의 의미는 다릅니다.

| 값·상태 | 가능한 의미 |
|---|---|
| 딕셔너리에 키가 없음 | 해당 필드가 아예 전달되지 않음 |
| `None` | 필드는 있으나 값이 없음 |
| `""` | 빈 문자열이 전달됨 |
| `0` | 실제 측정값이나 금액이 0 |
| `False` | 명시적인 거짓 상태 |

예를 들어 다음 코드는 금액이 정상적으로 `0`인 주문까지 누락으로 판단합니다.

```python
if not amount:
    ...
```

값이 `None`인지 확인하려는 목적이라면 다음처럼 구분해야 합니다.

```python
if amount is None:
    ...
```

또한 `row.get("amount")`는 키가 없는 경우와 값이 `None`인 경우를 구분하지 못합니다. 둘을 구분해야 한다면 `"amount" in row`를 함께 확인하세요.

### ② 대입·복사·함수 인자에서 원본 변경에 주의하기

Java 경험이 있어도 파이썬에서 다시 확인할 만한 부분입니다.

| 상황 | 알아야 할 점 |
|---|---|
| `b = a` | 새 객체를 복사하는 것이 아니라 같은 객체를 참조할 수 있음 |
| `b = a.copy()` | 얕은 복사이므로 내부의 리스트·딕셔너리가 공유될 수 있음 |
| 함수에 리스트·딕셔너리 전달 | 함수 안에서 객체를 수정하면 호출한 쪽에서도 변경이 보일 수 있음 |
| 함수 기본값을 `[]`로 선언 | 호출마다 새 리스트가 생기는 것이 아니라 기본 객체가 재사용됨 |
| 클래스 변수로 리스트 선언 | 여러 인스턴스가 같은 리스트를 공유할 수 있음 |

함수 기본값 문제는 다음 형태를 익혀두면 좋습니다.

```python
def collect_orders(orders=None):
    if orders is None:
        orders = []

    return orders
```

무조건 깊은 복사로 해결하기보다는 **“이 함수는 원본을 수정하는가, 새 결과를 반환하는가?”를 먼저 정하고 일관되게 구현**하세요.

### ③ 함수·클래스·타입 힌트는 역할을 구분하기

처음에는 다음 정도로 함수를 나누면 충분합니다.

- 읽기: 파일·API·DB에서 입력을 가져옴
- 검증·변환: 입력값을 검사하고 정리함
- 저장: 처리 결과를 외부에 기록함

특히 **변환 함수 안에 DB 저장과 API 호출을 섞지 않으면 테스트하기 쉬워집니다.**

클래스는 여러 함수가 공유하는 설정·상태를 함께 관리할 필요가 있을 때 적용하세요. 모든 기능에 클래스가 필요한 것은 아닙니다.

타입 힌트도 Java의 타입 검사와 동일하게 생각하면 안 됩니다. **타입 힌트 자체는 실행 중 입력을 자동 검증하거나 형 변환하지 않습니다.** 외부 데이터 검증은 별도로 구현해야 합니다. [Python 타입 힌트 문서](https://docs.python.org/3/library/typing.html)

### ④ 파일을 읽는 것과 데이터를 이해하는 것은 다르기

파일이 정상적으로 열려도 데이터가 올바르게 해석됐다는 뜻은 아닙니다.

| 데이터 | 주의할 점 |
|---|---|
| 고객 ID `"00123"` | 숫자로 바꾸면 앞의 0이 사라짐. 계산 대상이 아니라 식별자라면 문자열 유지 |
| 금액 `"1,200"` | 쉼표를 제거하기 전에 데이터의 숫자 표기 규칙부터 확인 |
| `"null"`과 JSON의 `null` | 전자는 문자열이고 후자는 파이썬에서 `None`으로 해석됨 |
| 날짜 `"03/04/2026"` | 월/일인지 일/월인지 입력 규칙 확인 |
| 한글이 포함된 CSV | UTF-8·CP949 등 실제 인코딩 확인 |
| JSON 파일과 JSONL 파일 | 하나의 JSON 문서인지, 한 줄마다 독립된 JSON 문서인지 구분 |

변환에 실패했다고 무조건 `0`이나 빈 문자열로 바꾸지 마세요. **실제 값이 0인 데이터와 변환 실패 데이터가 섞이기 때문입니다.**

### ⑤ 날짜·금액은 별도의 처리 규칙이 필요하기

날짜에서는 다음을 구분하세요.

- 시간대 정보가 없는 시각과 있는 시각
- 원본이 기록된 시간대와 집계에 사용할 시간대
- 날짜 문자열과 실제 시각
- 초 단위 타임스탬프와 밀리초 단위 타임스탬프

예를 들어 UTC 기준 밤의 주문이 한국 시간으로는 다음 날일 수 있습니다. 날짜별 집계를 한다면 **시간대를 변환한 뒤 날짜를 결정해야 하는지** 확인해야 합니다. [Python 날짜·시간 문서](https://docs.python.org/3/library/datetime.html)

금액은 원 단위 정수로 처리할지, 소수 금액을 `Decimal`로 처리할지 정하세요. `Decimal`을 사용할 때는 가능하면 원본 문자열에서 생성하고, 반올림 규칙도 명시합니다.

```python
from decimal import Decimal

amount = Decimal("1200.50")
```

이미 부동소수점으로 변환한 값에서 `Decimal`을 만들면 그 값의 오차가 전달될 수 있습니다. [Python Decimal 문서](https://docs.python.org/3/library/decimal.html)

### ⑥ 예외 처리는 오류를 숨기는 기능이 아니기

다음 형태는 특히 피해야 합니다.

```python
try:
    ...
except Exception:
    pass
```

프로그램은 끝났는데 일부 데이터가 사라진 상태가 될 수 있습니다.

| 오류 상황 | 권장 대응 |
|---|---|
| 특정 행의 날짜 형식 오류 | 사유를 기록하고 불량 데이터로 분리하거나, 정한 정책에 따라 작업 중단 |
| 일시적인 네트워크 오류 | 재시도가 안전한 요청인지 확인하고 제한된 횟수로 재시도 |
| 잘못된 인증정보·설정 | 계속 재시도하지 말고 설정 오류를 드러내기 |
| 예상하지 못한 코드 오류 | traceback을 남기고 실패를 호출자에게 전달 |

API 호출 실패를 단순히 `[]`로 반환하는 것도 주의하세요. 호출한 쪽에서는 **“정상 조회 결과가 0건”인지 “조회에 실패한 것”인지 구분할 수 없습니다.**

처리할 수 있는 예외를 구체적으로 잡고, 예상하지 못한 예외는 전파하는 방식을 익히세요. [Python 예외 처리 문서](https://docs.python.org/3/tutorial/errors.html)

### ⑦ 로그에는 실행 결과를 판단할 정보가 있어야 하기

`시작`, `종료`만 남기면 데이터 처리 결과를 판단하기 어렵습니다.

최소한 다음 내용을 남겨보세요.

- 실행 식별자 또는 작업명
- 처리 대상 파일·날짜
- 입력 건수
- 정상·불량·중복 건수
- 저장 건수
- 소요 시간
- 실패 단계와 예외 정보

비밀번호·API 토큰·불필요한 개인정보는 기록하지 마세요.

또한 두 작업을 구분해야 합니다.

- **실행 로그 작성:** 내가 만든 프로그램이 무엇을 했는지 기록
- **로그 데이터 처리:** 다른 프로그램이 만든 로그를 읽고 필드를 추출·집계

처음에는 실행 로그 작성부터 익히고, 이후 샘플 로그에서 시간·상태 코드·오류 메시지를 추출해보면 됩니다. [Python logging 문서](https://docs.python.org/3/library/logging.html)

### ⑧ 제너레이터·청크 처리가 메모리 문제를 자동으로 해결하지는 않기

다음 차이를 이해해야 합니다.

| 처리 방식 | 메모리 관점 |
|---|---|
| 파일 전체를 `read()` 또는 `readlines()`로 읽음 | 전체 내용이 메모리에 올라감 |
| 파일을 한 줄씩 순회 | 입력을 조금씩 읽을 수 있음 |
| `yield`로 한 건씩 전달 | 결과 전체를 먼저 만들지 않고 전달 가능 |
| 제너레이터 결과를 `list(...)`로 변환 | 결국 전체 결과가 메모리에 올라감 |
| 청크별 결과를 계속 리스트에 추가 | 입력을 나눠 읽어도 누적 결과 때문에 메모리가 증가함 |

추가로 알아둘 점은 다음과 같습니다.

- 제너레이터는 한 번 끝까지 소비하면 다시 처음부터 순회되지 않습니다.
- `sorted()`는 전체 정렬 결과를 만들기 때문에 단순 스트리밍과 다릅니다.
- 중복 확인용 `set`도 서로 다른 ID가 계속 늘면 메모리를 사용합니다.
- 청크별 집계를 합칠 때는 계산 방식이 중요합니다. 예를 들어 **청크별 평균의 단순 평균은 전체 평균과 다를 수 있습니다.**

pandas 공식 문서도 청크 간 조정이 적은 작업과 복잡한 작업을 구분합니다. [pandas 메모리·청크 처리 가이드](https://pandas.pydata.org/docs/user_guide/scale.html)

### ⑨ API·DB 연동은 성공 경로와 실패 경로를 함께 배우기

**API에서 확인할 것**

- HTTP 성공 여부와 JSON 해석 성공 여부는 별개입니다.
- 페이지네이션의 마지막 페이지를 어떻게 판단하는지 확인해야 합니다.
- `requests`는 타임아웃을 명시하지 않으면 기본적으로 타임아웃이 없습니다.
- 연결·읽기 타임아웃은 전체 작업의 총 소요 시간 제한과 같지 않습니다.
- 재시도 횟수와 대기 시간을 제한하고, POST처럼 중복 실행이 문제를 만들 수 있는 요청은 특히 주의해야 합니다. [Requests 공식 문서](https://requests.readthedocs.io/en/latest/user/quickstart/)

**DB에서 확인할 것**

- 값은 f-string으로 SQL에 끼워 넣지 말고 드라이버의 매개변수 바인딩을 사용합니다.
- 드라이버마다 매개변수 표기와 커서 동작이 다를 수 있습니다.
- INSERT를 실행한 것과 트랜잭션이 커밋된 것은 다릅니다.
- 자동 커밋 여부와 실패 시 롤백 범위를 확인합니다.
- 데이터를 몇 건씩 조회·저장할지 정합니다.
- 같은 입력을 다시 저장했을 때 중복·변경을 어떻게 처리할지 확인합니다. [MySQL 매개변수 바인딩](https://dev.mysql.com/doc/connector-python/en/connector-python-api-mysqlcursor-execute.html), [커밋 동작](https://dev.mysql.com/doc/connector-python/en/connector-python-api-mysqlconnection-commit.html)

### ⑩ pandas는 함수 이름보다 결과의 의미를 확인하기

pandas에서는 특히 다음을 확인하세요.

| 작업 | 확인할 질문 |
|---|---|
| 파일 읽기 | ID·날짜·금액의 자료형이 의도대로 읽혔는가? |
| 결측값 처리 | 값을 채우거나 행을 제거할 근거가 있는가? |
| 중복 제거 | 어느 열을 기준으로 같은 데이터라고 판단하는가? |
| 병합 `merge` | 병합 키가 유일한가? 예상보다 행이 늘어나지 않았는가? |
| 집계 `groupby` | 합계·평균·건수의 의미가 맞는가? |
| 형 변환 실패 처리 | 실패한 값이 결측값으로 바뀌면서 조용히 누락되지 않았는가? |

예를 들어 같은 고객 ID가 왼쪽 표에 2행, 오른쪽 표에 3행 있다면 병합 후 해당 ID의 결과가 6행으로 늘어날 수 있습니다. `merge`의 `validate`를 이용해 예상한 일대일·다대일 관계인지 검사하는 방법도 익히세요. [pandas 병합 문서](https://pandas.pydata.org/docs/user_guide/merging.html)

## 3. 공부한 내용을 확인하는 실습 순서

모든 문법을 외웠는지가 아니라, 아래 결과물을 만들 수 있는지로 확인하세요.

| 구간 | 확인용 실습 | 통과 기준 |
|---|---|---|
| 0~6번 | 메모리 안의 주문 목록 처리 | 자료구조를 선택하고, 필터·정렬·집계를 함수로 나누며, 원본 변경 여부를 설명할 수 있음 |
| 7~15번 | CSV 정제 → JSONL 저장 | 오류 행을 구분하고, 실행 로그와 테스트를 작성하며, 전체 파일을 한꺼번에 읽지 않는 방식을 구현할 수 있음 |
| 16~19번 | API 수집 → DB 저장 / pandas 집계 | 페이지네이션·오류·트랜잭션을 처리하고, 집계 결과를 작은 수작업 예시와 비교할 수 있음 |
| 20~22번 | 필요한 선택 실습 | 프로젝트에 필요할 때 재귀·스크래핑·추가 심화를 적용 |

테스트에는 최소한 다음 입력을 넣어보세요.

- 정상 데이터
- 빈 입력
- 필수 값 누락
- 실제 값이 `0`인 데이터
- 잘못된 날짜·숫자
- 중복 ID
- 한글·쉼표·줄바꿈이 포함된 문자열
- 외부 호출 실패

테스트는 함수 학습 직후부터 간단한 것부터 붙여도 됩니다. 표에서 뒤에 배치한 것은 파일·예외까지 포함한 테스트를 확장하는 시점이라는 의미입니다. [pytest 시작하기](https://docs.pytest.org/en/stable/getting-started.html)

**지금은 실행 환경을 확인하고, 1번은 짧게 복습한 뒤 2번 자료구조부터 시작하면 됩니다.** 각 항목마다 “작은 예제 구현 → 입력을 바꿔보기 → 일부러 실패시키기 → 원인을 설명하기”까지 해보고 넘어가세요. 이 목록 전체를 암기하는 것보다, 앞에서 만든 프로그램에 한 기능씩 추가하는 방식이 적합합니다.
